--- construir
titulo: Un contrato, dos motores
objetivo: Definir el DAO de hábitos y registros con dos implementaciones (memoria y fichero) que pasan las mismas pruebas.
reto:
1. Define:

```java
public interface HabitoDao {
    Habito guardar(Habito h);              // crea o reemplaza por id
    Optional<Habito> buscar(String id);
    List<Habito> listar();
    boolean borrar(String id);
}
```

y lo mismo para `RegistroDao` (con `listarPorHabito(String habitoId)`).

2. `HabitoDaoMemoria`: sobre tu `MiHashMap`.
3. `HabitoDaoFichero`: guarda en `datos/habitos.csv` (una línea por hábito). Al crearse, carga el fichero si existe; en cada cambio, lo reescribe entero.
4. **Prueba de contrato:** un método `probarContrato(HabitoDao dao)` con 8 checks, que llamas una vez con cada implementación.

El `Objetivo` de cada hábito también hay que guardarlo como texto, por ejemplo `DIAS_MINIMOS:4` o `MEDIA_MINIMA:7.0`. Crea `Objetivo.desdeTexto(String)` y `aTexto()`.
hecho:
- `probarContrato` pasa con las dos implementaciones sin cambiar ni una línea.
- Si descartas un `HabitoDaoFichero` y creas otro, los hábitos siguen ahí.
- Un hábito con objetivo `MediaMinima(7.0)` se guarda y se recupera igual.
minima:
Solo `HabitoDaoMemoria` y la prueba de contrato.
pista1:
`Files.createDirectories(ruta.getParent())`, `Files.readAllLines(ruta)` y `Files.write(ruta, lineas)`. Con `Files.exists(ruta)` sabes si es la primera vez.
pista2:
Formato: `id;nombre;tipo;objetivo`. ¿Y si un nombre contiene `;`? Tienes dos opciones: escaparlo o prohibirlo en el constructor de `Habito`. Prohibirlo es un invariante más, y te ahorra el problema (semana 1).
pista3:
`desdeTexto` es una pequeña fábrica: separa por `:` y, con un `switch` sobre la primera parte, crea la implementación correcta (`case "DIAS_MINIMOS" -> new DiasMinimos(Integer.parseInt(partes[1]));`). Es el único sitio del código donde se permite un switch por tipo, porque es donde nacen los objetos.

--- medir
titulo: Reescribir todo frente a añadir al final
objetivo: Medir dos formas de guardar registros en fichero y entender por qué las bases de datos usan logs append-only.
reto:
Implementa dos versiones de `RegistroDao` en fichero:

- **Reescritura:** cada `guardar` reescribe el fichero entero con todos los registros.
- **Append-only:** cada `guardar` añade una línea al final: `Files.writeString(ruta, linea + "\n", StandardOpenOption.CREATE, StandardOpenOption.APPEND)`.

Con el Complejómetro, inserta n registros uno a uno (n = 1 000, 2 000 y 4 000). Compara también con `RegistroDaoMemoria`.

Después piensa en la pega del append-only: ¿cómo borras un registro? (Pista: no lo borras.)
hecho:
- La k de las dos versiones de fichero apuntada (≈2 frente a ≈1).
- El tiempo por operación en memoria frente a fichero.
- Has diseñado (en papel o en código) cómo borrar en un log append-only.
minima:
Reescritura frente a append-only con n = 2 000 y 4 000.
pista1:
Reescribir n registros en cada inserción supone 1 + 2 + … + n líneas escritas: O(n²) en total. Añadir una línea: O(1) por inserción.
pista2:
Para borrar en append-only se añade una línea "lápida": `BORRADO;id`. Al cargar, se lee el log entero de principio a fin y se aplican las operaciones en orden. Es la idea del Write-Ahead Log de PostgreSQL y del log de Kafka.
pista3:
La pega: el log crece para siempre y cargar se vuelve lento. La solución es la **compactación**: de vez en cuando se reescribe el fichero con solo el estado actual. Es lo mismo que hace tu reescritura, pero de vez en cuando en lugar de en cada operación.

=== SEMANA 12
bloque: 3
titulo: Patrones que ya usas (y Observer)
resumen: Llevas semanas aplicando patrones de diseño sin ponerles nombre. Esta semana los identificas en tu propio código, añades uno nuevo (Observer) y mides lo único que importa de un patrón: cuánto cuesta cambiar el código.
sabes:
- `Objetivo` (semana 2), `Comando` (semana 7), el DAO y `desdeTexto` (semana 11).
- Interfaces y composición.
nuevo:
- Strategy, Command y Factory: ponerle nombre a lo que ya hiciste.
- Observer: avisar a quien le interese sin conocerlo.
- Records de Java para eventos inmutables.
- Medir el coste de cambio (archivos y líneas tocadas).
objetivos:
- Tener un mapa de los patrones de tu tracker.
- Construir un bus de eventos y conectarle 3 oyentes.
- Comparar con `git diff --stat` cuánto cuesta añadir una funcionalidad con y sin eventos.
tracker: `BusEventos` con oyentes de rachas, logros y auditoría.

--- construir
titulo: El bus de eventos
objetivo: Construir un sistema de publicación de eventos (Observer) y crear el mapa de patrones de tu tracker.
reto:
**Parte 1. Mapa de patrones (10 min).** En la libreta, identifica en tu código:

- **Strategy:** algo que elige un comportamiento intercambiable.
- **Command:** acciones convertidas en objetos.
- **Factory:** un método que decide qué clase crear.
- **DAO:** acceso a datos detrás de una interfaz.

**Parte 2. Bus de eventos.**

```java
public interface Evento {}
public record HabitoMarcado(String habitoId, LocalDate fecha, double valor) implements Evento {}
public record HabitoDesmarcado(String habitoId, LocalDate fecha) implements Evento {}

public interface Oyente { void recibir(Evento e); }

public final class BusEventos {
    public void suscribir(Oyente o) { ... }
    public void publicar(Evento e) { ... } // avisa a todos los oyentes
}
```

Cada oyente decide qué eventos le interesan con pattern matching: `if (e instanceof HabitoMarcado m) { ... m.habitoId() ... }`.
hecho:
- Los 4 patrones localizados, con el nombre de la clase de tu código.
- Un oyente de prueba recibe los eventos publicados (con checks).
- Un oyente que lanza una excepción no impide que los demás reciban el evento.
minima:
Solo la parte 1, o solo el bus con un oyente que imprime.
pista1:
Strategy → `Objetivo`. Command → `Comando` del historial. Factory → `Objetivo.desdeTexto`. DAO → `HabitoDao`. Llevas usando patrones desde la semana 2.
pista2:
Un `record` es una clase inmutable en una línea: Java genera el constructor, los getters (`habitoId()`), `equals`, `hashCode` y `toString`. Es exactamente lo que escribiste a mano en `Registro` en la semana 1.
pista3:
Para que un oyente roto no afecte al resto:
```java
public void publicar(Evento e) {
    for (Oyente o : oyentes) {
        try { o.recibir(e); }
        catch (RuntimeException ex) { System.err.println("Oyente falló: " + ex.getMessage()); }
    }
}
```

--- medir
titulo: El coste de cambio
objetivo: Medir con git cuánto cuesta añadir una funcionalidad con y sin eventos, y el coste en tiempo de publicar un evento.
reto:
**Funcionalidad:** "cuando un hábito llegue a 7 días seguidos, imprime `RACHA 7: gym`".

1. Haz un commit del estado actual. En una rama `sin-eventos`, impleméntala **sin** el bus, modificando directamente `TrackerService.marcar`. Apunta el resultado de `git diff --stat`.
2. Vuelve a la rama principal. En una rama `con-eventos`, impleméntala con un oyente nuevo y una línea para suscribirlo. Apunta `git diff --stat`.
3. **Rendimiento:** publica 1 000 000 de eventos con 0, 1, 10 y 100 oyentes. Apunta los ns por evento.
hecho:
- Los dos `git diff --stat` apuntados: archivos modificados frente a archivos nuevos.
- La tabla de ns por evento según el número de oyentes.
- Una frase con tu conclusión: ¿cuándo compensa el bus?
minima:
Solo los pasos 1 y 2.
pista1:
Fíjate menos en el número de líneas y más en esto: ¿has **modificado** código que ya funcionaba o solo has **añadido** código nuevo? Modificar es donde se cuelan los bugs (abierto/cerrado, semana 2).
pista2:
El coste de publicar debería crecer de forma lineal con los oyentes: es un bucle que llama a cada uno. Incluso con 100 oyentes triviales hablamos de cientos de nanosegundos o pocos microsegundos por evento: irrelevante para el tracker.
pista3:
La cara oculta del Observer: el flujo del programa ya no se lee de arriba abajo. Para saber qué pasa al marcar un hábito tienes que buscar quién está suscrito. Con 3 oyentes es comodísimo; con 50 repartidos por el código, depurar es un infierno. Eso también es coste de cambio.

--- aplicar

--- explica
reto:
Strategy, Command y Observer: explica con ejemplos de TU tracker qué problema resuelve cada uno. Después, pon un ejemplo concreto de cuándo usar un patrón sería sobreingeniería.
guia:
