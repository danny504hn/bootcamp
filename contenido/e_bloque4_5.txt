--- construir
titulo: Tu parser JSON
objetivo: Escribir un parser JSON recursivo descendente que convierte texto en Map, List, String, Double, Boolean y null.
reto:
Crea `json.JsonParser`:

```java
public static Object parse(String texto)
```

Estructura: una clase con un `String s` y un índice `int pos`, y un método por cada regla de JSON:

- `valor()`: mira el carácter actual y decide qué método llamar.
- `objeto()`, `array()`, `cadena()`, `numero()` y `literal()` (true, false, null).
- `saltarEspacios()`.

Los errores lanzan una `JsonException` con la posición: `"Esperaba ':' en la posición 14"`.

**Prueba de ida y vuelta:** con 5 estructuras distintas (una de ellas anidada a 3 niveles), comprueba que `parse(Json.escribir(x)).equals(x)`. Usa números `Double` en las pruebas, porque tu parser siempre devuelve Double.
hecho:
- Las 5 pruebas de ida y vuelta pasan.
- `parse("{\"a\": }")` lanza una `JsonException` con una posición útil.
- Los espacios y saltos de línea entre elementos no afectan.
minima:
Solo objetos planos con valores de texto y número (sin anidar ni arrays).
pista1:
Mira el carácter actual para decidir: `{` → objeto, `[` → array, `"` → cadena, `t`/`f`/`n` → literal, `-` o un dígito → número. Cada método consume su parte y deja `pos` justo después. La pila de llamadas lleva la cuenta del anidamiento: es tu validador de paréntesis, pero con la pila implícita.
pista2:
```java
private Map<String, Object> objeto() {
    esperar('{');
    Map<String, Object> m = new LinkedHashMap<>();
    saltarEspacios();
    if (actual() == '}') { pos++; return m; }
    while (true) {
        saltarEspacios();
        String clave = cadena();
        saltarEspacios(); esperar(':');
        m.put(clave, valor()); // valor() empieza saltando espacios
        saltarEspacios();
        if (actual() == ',') { pos++; continue; }
        esperar('}');
        return m;
    }
}
```
pista3:
`numero()`: avanza mientras el carácter esté en `-+.eE0123456789` y después haz `Double.parseDouble(s.substring(inicio, pos))`. `cadena()`: usa un `StringBuilder`; si encuentras una `\`, mira el carácter siguiente (`"`, `\`, `n`, `t`…) y añade el carácter real. `\uXXXX` es una misión secundaria: `(char) Integer.parseInt(hex, 16)`.

--- construir
titulo: Dos servicios, dos procesos
objetivo: Separar el tracker en un servicio de hábitos y otro de estadísticas que se comunican por HTTP.
reto:
- **servicio-habitos** (puerto 8081): hábitos y registros, con sus propios ficheros. Es el dueño de esos datos.
- **servicio-estadisticas** (puerto 8082): `GET /rachas` y `GET /informe/semana`. No tiene acceso a los ficheros del otro: le pide los datos a 8081 por HTTP con `HttpClient`.

Cada uno tiene su propio `main` y se arranca por separado. Reutiliza tu router, tu JSON y tus DAO.
hecho:
- Los dos procesos arrancan por separado y `GET :8082/rachas` devuelve datos reales de 8081.

pista2:

--- medir
titulo: El precio de la red
objetivo: Medir cuánta latencia añade partir el sistema y qué pasa cuando un servicio cae.
reto:
1. Con tu `Carga`, compara p50 y p99 de `GET /informe/semana` en el monolito (semana 16) y en el sistema distribuido.
2. **Apaga servicio-habitos** y llama a `:8082/informe/semana`:
   - sin timeout: ¿cuánto tarda en fallar?
   - con `HttpRequest.newBuilder(...).timeout(Duration.ofMillis(500))`
3. Simula un servicio lento: `Thread.sleep(2000)` en un endpoint de 8081. ¿Qué pasa con las peticiones a 8082?
hecho:
- La tabla de monolito frente a distribuido (p50 y p99).
- El tiempo hasta el error, con y sin timeout.
- Sabes qué es un fallo en cascada.
minima:
Solo el punto 1.
pista1:
Con el proceso apagado, la conexión se rechaza al instante (`ConnectException`). Lo peligroso no es un servicio caído sino un servicio **lento**: sin timeout, cada petición a 8082 se queda esperando, se acumulan y acabas tumbando también 8082. Eso es un fallo en cascada.
pista2:
Configura dos timeouts: el de conexión (`HttpClient.newBuilder().connectTimeout(...)`) y el de la petición completa (`HttpRequest...timeout(...)`). Cuando expira, `HttpClient` lanza `HttpTimeoutException`.
pista3:
Lo habitual es que cada salto de red local añada entre 0,5 y 2 ms al p50, y bastante más al p99. Con 5 servicios encadenados, eso se multiplica. Es el coste real que pagas por la independencia de despliegue.

--- aplicar
titulo: Fallar con elegancia
objetivo: Hacer que servicio-estadisticas sobreviva a los fallos de servicio-habitos.
reto:
1. **Timeout + 1 reintento** con una espera de 100 ms en `ClienteHabitos`.
2. **Respuesta degradada:** si hábitos no responde, `GET /rachas` devuelve **503** con `{"error": "El servicio de hábitos no está disponible", "reintentar_en_s": 5}` en lugar de quedarse colgado o devolver un 500.
3. **Caché del último valor conocido:** si falla, devuelve las últimas rachas calculadas con un campo `"desactualizado": true`.
4. **Misión secundaria:** webhooks. servicio-habitos avisa con `POST :8082/eventos` cada vez que se marca un hábito (tu Observer de la semana 12, pero entre procesos), y estadísticas actualiza las rachas sin tener que preguntar.
hecho:
- Con servicio-habitos apagado, `:8082/rachas` responde en menos de 1 s.
- La respuesta degradada lleva el código y el JSON correctos.
- Cuando vuelves a arrancar servicio-habitos, todo se recupera solo.
minima:
Solo el timeout y la respuesta 503.
pista1:
Un reintento sirve para fallos momentáneos, pero reintentar sin límite contra un servicio sobrecargado lo empeora. Por eso: pocos reintentos, con espera entre ellos y siempre con timeout.
pista2:
La caché del último valor: un campo `volatile Map<String, Object> ultimasRachas` que actualizas cada vez que el cálculo sale bien. En el `catch`, si no es null, lo devuelves con `"desactualizado": true`.
pista3:
Con los webhooks inviertes la dependencia: estadísticas ya no pregunta, le avisan. Pero aparece un problema nuevo: ¿y si estadísticas está caído cuando llega el aviso? Las soluciones reales (colas de mensajes como Kafka o RabbitMQ) usan algo que ya conoces: un log append-only (semana 11).
